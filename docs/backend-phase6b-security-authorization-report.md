## B. Threat model and actual boundaries

### Identity/session ledger

All accounts and resource IDs were newly generated by the fixture, not guessed production identifiers. Session tokens/passwords were generated in memory, stored only in the disposable test database as appropriate, and never included in results/reports.

| Actor alias | Workspace A | Workspace B | Purpose |
|---|---|---|---|
| viewer | VIEWER | None | Read positive, mutation negative |
| qa | QA | None | Normal mutations and cross-workspace negatives |
| lead | QA_LEAD | None | Finalize positive, admin negative |
| admin | ADMIN | None | Workspace management positive, OWNER restriction negative |
| owner | OWNER | None | Permitted membership change positive |
| foreign | None | OWNER | Foreign-resource positive and A-resource negative |
| multi | ADMIN | VIEWER | Strong A role must not authorize a B mutation |
| none | None | None | Authenticated without a relevant membership |

Two workspaces contain Project A and A2 in A, Project B in B. Each project has a testcase, Bug, run, execution, evidence metadata, report, requirement and automation telemetry. Testcases intentionally share the project-local display ID `SHARED-001`; their internal IDs remain distinct. Assertions resolve ownership through persisted IDs/relationships.

### Architecture

- Login verifies a salted scrypt password; the server generates a random cookie session token. Only its SHA-256 hash is stored. Protected requests reload the user and workspace memberships from the database. Expired, revoked, invalid or disabled-user sessions are denied; role downgrade/removal is effective on the next request.
- Roles are workspace-scoped: VIEWER < QA < QA_LEAD < ADMIN < OWNER. There is no inferred global ADMIN privilege over every workspace. Multiple projects inside one authorized workspace are allowed; no per-project membership policy was invented.
- `src/proxy.ts` is the primary external request authorization boundary: session, mutation origin, project resolution, minimum role, then trusted actor-header propagation. Most internal handlers/services deliberately depend on that boundary rather than individually authenticating again.
- Projects listing filters using the trusted actor's user ID; project creation uses the trusted selected workspace. Workspace member handlers additionally require ADMIN and scope membership IDs to that workspace; granting/modifying OWNER requires OWNER.
- Report IDs, run IDs and other path IDs resolve their project from the database. Testcase/Bug bulk IDs resolve every existing referenced project's ownership, not merely the first record. Nested execution/evidence and relation handlers additionally constrain parent/child relationships in database queries.
- Client-supplied `x-qa-*` identity/role headers are overwritten by the real proxy; spoof attempts failed both before and after the patch. No header-spoofing vulnerability is claimed. Directly invoking a handler without that trusted boundary is not an externally supported API path.
- Host AI settings are read-only over HTTP: even ADMIN PUT returns 405. GET currently follows the existing viewer-read policy. No policy redesign was performed.

## D. Confirmed findings and fixes

### 6B-SCOPE — High: authorized ID unlocked an unscoped collection

- Preconditions: actor has VIEWER or higher in A, no B membership; knows one own testcase/Bug ID.
- Baseline: `GET /api/testcases?id=CASE_A` or equivalent Bugs request let the proxy derive A, but the handler ignored `id` and omitted its project filter. Integration returned 200; production HTTP explicitly contained the foreign generated record ID.
- Expected: an ID must not authorize an unfiltered cross-workspace list.
- Fix: explicit project required for Cases/Bugs collection reads, with a shared proxy collection guard also covering Modules. Existing project-filtered clients keep their response shape/defaults.
- Evidence: baseline production 200 + foreignRecordExposed=true; fixed production 400 + false. Both Cases/Bugs regressions and the adjacent Modules test pass.

### 6B-QUERY-BODY — High: query project shadowed an unauthorized JSON body project

- Actor: QA in A only. Target: B.
- Baseline: POST testcase with an authorized A query and B in the JSON body. Proxy chose query OR body, but handler created in B. SQLite read-back showed a new foreign testcase and CREATED activity under the A actor. Production HTTP returned 201 and foreign-record count increased by one.
- Fix: collect and authorize all supplied query project values and the body project independently. An authorized value cannot hide another workspace. This does not forbid operations across two projects within the same workspace when both are otherwise permitted.
- Regression: fixed response 403; complete business snapshot unchanged; HTTP foreignRecordDelta=0.

### 6B-BODY — High: ignored JSON bodies bypassed ID authorization

- Actor: QA in A only. Target: FIXING Bug/source testcase in B.
- Baseline: send JSON under text/plain with authorized query project A. The proxy skipped the body but `req.json()` in the handler accepted it, then atomically changed foreign Bug/source/history. Production HTTP 200 and persisted foreign status changed. The oversized-body skip reproduced the same issue in integration.
- Fix: fail closed with 415 for unsupported JSON-handler media types, 400 for malformed/non-object JSON, and 413 for oversized bodies. The 1,000,000-byte bound is checked on declared length **and actual streamed bytes**, not just a user-controlled header. No body is silently ignored. Multipart bypass is allowed only for the handlers that actually consume multipart.
- Regression: plain, declared-oversize and missing-length oversized body tests leave snapshots unchanged; fixed HTTP text/plain returns 415 without changing the foreign Bug. This is targeted boundary testing, not load testing.

### 6B-PATH — High: encoded direct ID skipped stored report ownership

- Preconditions: authenticated member of A only; known foreign report ID.
- Baseline: percent-encode one character of B's report ID, supply query project A. Proxy lookup used the encoded spelling, found no report and accepted A; the framework decoded the dynamic handler parameter and returned B's report. Reproduced through the original production HTTP stack with generated CUIDs: 200 and foreign record exposed.
- Fix: normalize path segments once for authorization, matching framework parameter decoding. Stored report lookup is fail-closed with 404 if unresolved even when an explicit project was supplied.
- Regression: integration and fixed HTTP return 403 for the existing foreign report, with no restricted content. Other nested handlers retain their explicit parent/project checks.

### 6B-EVIDENCE — High: project-local display ID selected foreign telemetry

- Actor: A member reading a valid A evidence report; A/B share a display ID.
- Baseline: candidate IDs included the display ID, and devlog/recording lookups omitted project ownership. The more recent B run won; original production HTML contained the synthetic B private-log marker, not A's own marker.
- Fix: select devlog runs by authorized project; select recordings through run.projectId; use internal canonical IDs only for DB/file candidates; add a Bug's source ID only after confirming it belongs to the same project. A valid parent cannot authorize an unrelated source or ambiguous display-ID file.
- Regression: fixed production HTML 200 contains A's marker and no B marker. Normal own evidence remains usable.
- Compatibility: ambiguous legacy telemetry keyed only by display ID is intentionally no longer guessed. UUID-keyed data remains supported; any recovery of ambiguous legacy data needs a separately authorized ownership-aware migration. No UUID or recording was rewritten/deleted.

### 6B-MULTIPART — High: foreign Excel form project differed from authorized query

- Actor: QA in A only. Target: B's testcase/import history.
- Baseline: multipart preview could inspect B's existing-ID metadata while query authorized A. With a correctly formed synthetic workbook, the original production import returned **201** and added one testcase to B.
- Fix: the form project must exactly match the query project already authorized by the proxy, before workbook handling or notification-project assignment. Conflict returns 400 without foreign records/history/notifications.
- Regression: fixed HTTP returns 400, foreignRecordDelta=0; integration proves own valid preview still returns 200 with canImport=true.

### 6B-MATCHER — Medium, conditional: filename-like API IDs bypassed proxy authentication

- Preconditions: a valid custom/legacy resource ID containing a static-looking suffix, e.g. a generated report ID extended with `.js`, exists in the database. Ordinary generated CUIDs do **not** contain that suffix; this is not a claim that every normal report ID bypasses authentication.
- Baseline: general matcher excluded static filename suffixes even beneath `/api/`. Unauthenticated production GET returned the synthetic custom-ID report with 200.
- Fix: an explicit `/api/:path*` matcher protects every API path regardless of suffix; static asset exclusions remain outside that rule.
- Regression: fixed HTTP is 401 without a session; the report's authorized workspace member can still read the same ID with 200. Confirmed for the stated valid-ID precondition, not generalized to normal-CUID auth bypass or unrelated framework CVEs.

### 6B-ERROR — Low: raw evidence exception echoed to client

- Preconditions: authorized evidence request encounters an internal error.
- Baseline: controlled handler fault injection returned the exception marker verbatim inside a 500 JSON body. This proves error-detail echo, not an SQL injection or exposure of an actual user's credentials.
- Fix: generic error response; diagnostic log retains a safe error code without raw exception content.
- Regression: fault injection remains 500 but response no longer contains the private marker. Not tested by inducing a failure in the production HTTP smoke.

Reproducibility: the seven authorization/ownership paths above were demonstrated on fresh production HTTP fixtures, then their corrected controls passed on another fresh fixture. The error echo uses handler fault injection. The first seven integration regressions all failed against pre-fix source; two additional multipart/error regressions also failed before their fixes. No unsafe real-user reproduction was performed.

Additional controls:

- Missing/invalid/expired/revoked/disabled session: 401, no business changes.
- Authenticated non-member: 403. A-only actor against B: 403 or child-not-found 404 as appropriate.
- ADMIN in A + VIEWER in B: B read allowed, B mutation denied 403. Role strength does not leak across workspaces.
- Session after role downgrade or membership removal respects new DB permissions immediately on the next request.
- ADMIN cannot grant OWNER (403); cannot edit a B membership using A's selected workspace (404). OWNER can perform a permitted own-workspace membership change.
- Membership-scoped multi-project A/A2 bulk update is allowed. Mixed A/B update/delete batches are rejected as a whole, with business/history snapshots unchanged. Duplicate/missing authorized IDs preserve Phase 6A matched-unique behavior.
- Wrong run/execution/evidence chain is denied 404. Mixed-child testcase assignment/execution/link attempts produce existing 400/500 validation failures but no partial state/history; those 500 classifications are noted below rather than misreported as ideal 403 responses.

- No snapshot-consistent authorization under simultaneous membership transfer/project deletion was promised. Membership changes are checked on subsequent requests; no new DB-level tenant authorization constraints were added.
- Main running services still use their current build. Isolated verification does not install/restart this patch on the user's application.

No unresolved Critical finding remains within the executed scenarios. Untested areas above are not certified secure. Any future broader security phase must reassess them rather than infer safety from this report.
